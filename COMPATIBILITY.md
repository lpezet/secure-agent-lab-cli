# Compatibility

What `sal` promises, to whom, and what a version bump means. This is the
written statement that 1.0 requires; it is published before 1.0 so that the
promises can be argued with while they are still cheap to change.

`sal` is versioned **separately from the stack**. `sal --version` prints both,
and this document is only about the first of them. A stack release is the
version of the security boundary; a `sal` release is the version of the tool
that installs and updates it. Nothing here says anything about what
`v1.9.0 → v1.10.0` of the stack did.

## The public surface

Wider than the flags, which is the part most likely to surprise. Four things
are promises, and three of them are files:

| Surface | Who else reads it | Breaking it means |
|---|---|---|
| command grammar and flags | scripts, CI, people | a script that worked stops working |
| `<project>/.sal/lab.json` | committed to a user's git history; read by whatever `sal` they have next month, and by their colleagues | a checkout stops resolving to its lab |
| `<lab>/.sal/installed.json` | **`scripts/check-drift.sh` in the stack repo**, run by someone who may never have installed `sal` | a drift check in another repo goes wrong or silent |
| the generated `compose.yaml` | regenerated by `sal upgrade`; read by `docker compose` | least contractual of the three, but it is where the boundary's wiring lives |

Everything else is internal: package layout, the shape of the temporary
directories a fetch uses, the exact wording of output. Output wording in
particular is **not** a promise — parse `--version`, exit statuses and the
documented file formats, not prose.

## Exit statuses

| Status | Meaning |
|---|---|
| 0 | the command did what it says |
| 1 | it did not, and said why on stderr |
| 2 | (test harnesses only) a prerequisite is missing, distinguishable from a failed assertion |

`sal drift` exits **1 on findings**, which is what makes it usable as a CI
step. A command that reports a problem and exits 0 is the failure mode this
tool exists to avoid, so no command does it.

## The two JSON formats

Both carry a required `schema_version`, an **integer**, currently `1`. The rule
is the stack's own, adopted for the same reason it was adopted there for bank
manifests: **support a fixed set of generations and refuse anything above it.**
A file from the future may carry a field this build does not know to honour,
and acting on the part it understands while ignoring the rest is how a control
gets silently dropped. Absence is refused too — guessing once which generation
an unversioned file is would make that guess permanent.

### `<project>/.sal/lab.json` — generation 1

```json
{ "schema_version": 1, "name": "api-3f2a1b0c", "stack_tag": "v1.9.0" }
```

Three fields, all required. It is committed, so it **describes no machine**:
no absolute paths, no username, nothing that differs between two checkouts of
the same repository. `name` is `<basename>-<8 hex of the project's absolute
path>`; the hash makes two projects called `api` resolve to different labs, and
it is not reversible, which is why the lab records the project separately.

### `<lab>/.sal/installed.json` — generation 1

```json
{
  "schema_version": 1,
  "stack_tag": "v1.9.0",
  "stack_commit": "0123…",
  "project_dir": "/home/dev/projects/api",
  "installed": [
    {
      "name": "acme",
      "slot": 10,
      "schema_version": 1,
      "files": ["broker/acme.js", "proxy/010_acme.py", "cred-gateway/acme.conf"],
      "stack_tag": "v1.9.0",
      "source": "local",
      "installed_at": "2026-08-15T12:00:00Z"
    }
  ],
  "base_addons": ["000_policy.py", "001_allowlist.py"]
}
```

`schema_version`, `stack_tag` and `installed` are required; the rest are
optional and a reader must cope with their absence. `installed` lists **bank
entries only** — a proxy addon that came from the stack itself is in
`base_addons`, because `check-drift.sh` reads `installed` to decide which bank
entries a deployment claims and a stack addon there sends it looking for an
entry that does not exist.

**Adding an optional field here is not a generation event.** That is the
opposite of the rule for bank manifests, and the difference is one line of
code rather than a judgement call: a manifest is decoded with
`DisallowUnknownFields`, so a new field makes every older `sal` fail to read it
at all, while this file is decoded plainly, so an older `sal` ignores what it
does not know and still answers correctly every question it asks. A field that
changes the meaning of an existing one, or that a reader must honour to stay
correct, **is** a generation event wherever it lives.

## What a version bump means

`sal` follows SemVer over the surface above.

**Major** — a promise is withdrawn:

- a command or flag is removed, renamed, or given a different meaning
- a JSON format's generation is raised, i.e. an older `sal` can no longer read
  a file this one writes
- an exit status changes what it means
- the minimum stack version rises past what an existing deployment can be
  expected to have

**Minor** — something is added and nothing is withdrawn: a new command, a new
optional flag, a new optional field in `installed.json`, support for an
additional schema generation, a new stack release the CLI knows about.

**Patch** — behaviour is corrected without changing the surface. A bug fix that
changes output wording is a patch, because wording is not part of the surface.

**Pre-1.0 (now).** Anything may change in a minor release, and the release page
says so: every 0.x release is published as a pre-release. In one week
`--offline` and `--refresh` were removed in favour of `--stack-dir`, a bank
cache was introduced and then deleted entirely, `installed.json` gained
`base_addons`, and lab discovery moved from project-local to two trees. Each
would have been a major bump. The design is settling, not settled.

## What 1.0 means

Five things, all of them checkable:

1. **Every command in the grammar works, or is removed from the grammar.**
   Done: `internal/cli`'s `TestEveryCommandInTheGrammarIsImplemented` fails on
   any command still wired to `notImplemented`, and its allowlist is empty.
2. **Both JSON formats declared stable at their current generation.** This
   document is that declaration; what it needs is time at generation 1 without
   another field being wanted.
3. **The `lab_setup` question resolved.** Fragments install today and nothing
   sources them, so a bank entry that ships one installs without fully working.
4. **The install script exercised against a real published release.** Its
   refusals are tested (`tests/install/`), but no release has ever been
   downloaded by it.
5. **This document**, kept current.

## Deprecation

Before a promise is withdrawn in a major release, the thing being withdrawn
warns for at least one minor release, and the warning names what to use
instead. A flag that is going away keeps working while it warns.

The exception is a **security** correction: if a behaviour widens the boundary,
it changes in the next release of any kind, and the release notes say what
changed and what to check. A deprecation period on a widened boundary is a
period during which the boundary is wrong.
